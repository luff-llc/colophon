### Findings

1. **Critical — §4.2, §6.3: Recovery rule allows escalating from a lower `recoverThreshold` to `control` and taking over a higher-threshold library**
   - **Problem:** In §4.2, `recoverThreshold` only has to be between 1 and the number of `recover` controllers, independently of `threshold`. In §6.3, the recovery rule allows adding new controllers with any roles (`control`, `approve`, `recover`) so long as existing controllers, thresholds, vault, and slots are unchanged. By contrast, the Swift reference (`Keyring.swift` lines 38–42 and `KeyringRules.thresholdFault` lines 129–135) enforces both that `threshold >= recoverThreshold` (when `recoverThreshold > 1`) and that when `recoverThreshold < threshold`, a recovery-added controller may hold **only** `"approve"` (`guard controller.roles.allSatisfy({ $0 == "approve" })`). Draft 0.4 omits both checks.
   - **Failure scenario:** A library is configured with `threshold: 2` (requiring two `control` keys) and `recoverThreshold: 1` (a single recovery key). A single compromised or stolen `recover` key signs one `keyring` entry under the recovery rule adding two new software keys with `roles: ["control"]`. Because existing controllers, `threshold`, `recoverThreshold`, `vault`, and existing slots are untouched, §6.3 accepts the entry. The attacker then uses the two newly added `control` keys to meet `threshold: 2` under the control rule, rotates the vault, and removes all legitimate controllers.
   - **Proposed fix:**
     - In §4.2, add: "When `recoverThreshold > 0`, `threshold` MUST be at least `recoverThreshold` (or if `recoverThreshold < threshold` is permitted for approve-only recovery, constrain §6.3 as below)."
     - In §6.3 (`keyring`, by recovery), append: "If `recoverThreshold < threshold`, every newly added controller MUST have `roles` equal to `["approve"]`; a recovery change may grant `control` or `recover` to a new controller only when `recoverThreshold >= threshold`."

2. **Critical — §6.3, §6.4: `control` controllers can be removed or demoted without vault rotation by changing `threshold`, `recoverThreshold`, or `roles` without changing `vault`**
   - **Problem:** §6.4 states: "Removing a controller, or taking a role away from one, MUST rotate the vault (§6.2). It's authorized only by the control rule. The removed controller's slots MUST be absent from the new keyring." However:
     1. If a controller only had a role taken away (demoted, e.g. from `["control", "approve"]` to `["approve"]`), is it a "removed controller" whose slots must be absent, or can it keep its slot to the *new* vault?
     2. More importantly, what if a controller is removed or demoted, `keyring.vault` is rotated to a new key, and the attacker includes a new slot in the new keyring that seals the *new* vault seed to the removed controller (or leaves a `combined` slot referencing it)? §4.2 says "Every slot names existing controllers", which prevents naming a completely removed controller, but if a controller is *demoted* (e.g., loses `control` or `approve` and keeps `recover`, or vice versa), §6.4 requires rotating the vault, yet the demoted controller is still in `controllers` and can be given a slot for the new vault—or conversely, if a controller with a slot is demoted to a role that shouldn't have vault access, nothing forbids keeping a slot for it.
     3. Conversely, in §6.2, `keyring` says: "If `keyring.vault` differs from the current vault, `shares` MUST seal every existing epoch to the new vault, and `epochs` MUST start a new epoch in every namespace sealed per §5.1." It does **not** forbid `keyring.vault` from being rotated to a *previously used* vault identity, nor does it require that `shares` and `epochs` be *absent* when `keyring.vault` does *not* change.
   - **Failure scenario:** Controller $A$ is removed in `seq` 5, rotating from $\text{Vault}_1$ to $\text{Vault}_2$. In `seq` 6, a colluding or compromised controller rotates `keyring.vault` back to $\text{Vault}_1$ (which differs from current $\text{Vault}_2$, satisfying "differs from the current vault"). Controller $A$, which still holds the seed for $\text{Vault}_1$ from before `seq` 5, can now decrypt every new epoch sealed in `seq` 6 and all historical epochs shared in `seq` 6, completely bypassing removal without appearing in `seq` 6's `controllers` or `slots`.
   - **Proposed fix:**
     - In §6.2 (`keyring`), state: "If `keyring.vault` equals the current vault, `shares` and `epochs` MUST be absent. If `keyring.vault` changes, its signing and agreement keys MUST be fresh (never used by any previous vault or member in this library), `shares` MUST seal every existing epoch to the new vault, and `epochs` MUST start a new epoch in every namespace sealed per §5.1."
     - In §6.4, clarify: "Removing a controller, or removing any role from an existing controller, MUST rotate the vault (§6.2)."

3. **Critical — §3.1, §5.2, §6.2, §7: Controller keys can be reused as `device`/`app` members or vault keys, and `vault` can be used as a controller or member, breaking role separation and operation attribution**
   - **Problem:** §4.1 states: "A controller key MUST NOT be the signing key of a member whose authenticated kind is `agent` or `server`. An entry that would make one a controller is invalid, and so is a grant that admits a controller's key as an agent or server." This explicitly allows a controller key to be the same key as a `device` or `app` member, or even the `vault` identity! Furthermore:
     1. In 0.3 §5 (kept by 0.4), operations are signed with raw ECDSA P-256 over the operation header body (`colophon/operation/3`), and envelopes are `{"body","signature"}`. If a `raw` controller key is also granted as a `device` member, or if a `webauthn` controller signs an operation using `assertion`, does §3 allow `webauthn` signatures on operations and requests, or only on authority entries? §3.1 says "Records can carry `cosignatures`... `assertion` and `cosignatures` are present only when used, so records that don't use them keep 0.3's shape." "Records" in 0.3 §2 covers authority entries, requests, and operations!
     2. In §5.1, every epoch is sealed in `seals: {recipientID: sealedKey}` to "exactly the vault and the active, unexpired members with read access to that namespace", where the vault's recipient ID is its key ID. If the vault has the same key ID as a member (or if a member requests the vault's public identity), `seals` map keys collide (`recipientID`), and revoking the member in `revoke` either fails or strips the vault from the recipient set!
     3. In 0.3 §4 (kept in §7), `revoke` checks `ensure(member_id != &self.root.id())` and `grant` checks `request.member.id() != self.recovery.id()`. With `root` and `recovery` gone in 0.4, there is no rule preventing a `grant` from admitting the current or historical `vault` key ID as a member.
   - **Failure scenario:** A user or attacker submits a `request` whose `member` public identity equals the library's `vault` public identity, and an `approve` controller approves it. Because `seals` is a JSON map keyed by `recipientID`, the epoch seal for the vault and the member share the single key `vaultID`. When the member is later revoked via `revoke`, the member is excluded from future epochs, or if vault wins, the revoked member (who holds the same key) still receives every epoch seal under `vaultID`.
   - **Proposed fix:**
     - In §4.1 and §5.1, require strict key separation across namespaces of principals: "The `vault` key ID MUST NOT equal any current or historical controller ID, member ID, or previous vault ID. A member's signing or agreement public key MUST NOT equal any current or historical controller key or vault key (regardless of whether the member kind is `device`, `app`, `agent`, or `server`)."
     - In §3.1, explicitly state which record types may use `assertion` and `cosignatures`: "Only authority records MAY carry `assertion` or `cosignatures`. Requests and operations MUST use a single `raw` signature with no `assertion` or `cosignatures`."

4. **High — §5.2: `combined` slot parts have no domain separation per part index or part type, and `sealed` parts reuse the outer slot's HPKE `info` and AAD**
   - **Problem:** Look closely at §5.2 for `combined` slots:
     - Common info string: `I = "colophon/vault-slot/4\n" ‖ libraryID ‖ "\n" ‖ vaultID ‖ "\n" ‖ kind ‖ "\n" ‖ join(controllers, ",")`.
     - For `combined`, the table says: "Each part is `{"kind":"sealed","sealed":…}` or `{"kind":"prf","salt":…}`, in `controllers` order. Each part yields a 32-byte secret: the HPKE plaintext, or the HKDF output as above. The key is HKDF-SHA256(IKM = the secrets concatenated in order, salt = empty, info = `I`, 32 bytes)."
     - First: What is the HPKE `info` and AAD for a `sealed` part inside a `combined` slot, and what is the HKDF `info` for a `prf` part inside a `combined` slot? "as above" refers to `I`! Notice that in the Swift reference (`VaultSlot.swift` and `VaultSlotPart.swift`), standalone PRF used `"colophon/vault-prf/1"`, combined parts used `"colophon/vault-part/1"`, and the combined wrapping key used `"colophon/vault-combined/1"`. In 0.4 §5.2, both the inner part derivation (`prf` part HKDF `info`, `sealed` part HPKE `info`/AAD) and the outer `combined` HKDF `info` and AES-GCM AAD use the **exact same string `I`**!
     - Second: If a `combined` slot has two parts for the same controller or two `sealed` parts in `controllers`, neither the part index `i` nor the specific controller ID for part `i` is bound in the inner HPKE `info`/AAD; they all share `I`. Worse, does `controllers` in a `combined` slot allow duplicate controller IDs, or must `controllers` be distinct? §5.2 does not say! And how many parts must a `combined` slot have? Swift (`KeyringRules.slotIncomplete`, line 144) requires `parts.count >= 2`, whereas 0.4 §5.2 allows 0 or 1 part!
   - **Failure scenario:**
     1. An implementer creates a `combined` slot with `parts: []` (0 parts) or 1 part. With 0 parts, `IKM` is empty (`""`), and the vault seed is encrypted under a deterministic key `HKDF-SHA256(IKM = "", salt = "", info = I)` derived purely from public strings (`libraryID`, `vaultID`, `controllers = []`), exposing the vault seed to anyone who reads the authority log!
     2. In a 2-part `combined` slot with two `sealed` parts `[C1, C2]`, both HPKE ciphertexts use the exact same `info = I` and `AAD = I`. An active attacker or buggy host can swap or replay inner part ciphertexts across positions if the same key is used, or two implementers will disagree on whether inner `sealed` parts use `kind = "sealed"` with `[C_i]` in `I` vs `kind = "combined"` with `[C1, C2]` in `I` ("as above" is ambiguous between reusing the outer `I` vs constructing a per-part `I` with that part's `kind` and single controller).
   - **Proposed fix:**
     - Require `controllers` in a `combined` slot to have at least 2 entries, all distinct controller IDs, and `parts.length == controllers.length`.
     - Specify distinct domain-separated info strings for parts vs the outer slot: e.g., for part $i$ (0-indexed) controlled by `controllers[i]`, define $I_i = \text{"colophon/vault-slot-part/4\n"} \mathbin{\Vert} \text{libraryID} \mathbin{\Vert} \text{"\n"} \mathbin{\Vert} \text{vaultID} \mathbin{\Vert} \text{"\n"} \mathbin{\Vert} i \mathbin{\Vert} \text{"\n"} \mathbin{\Vert} \text{part.kind} \mathbin{\Vert} \text{"\n"} \mathbin{\Vert} \text{controllers}[i]$, used as the HPKE `info`/AAD for a `sealed` part and the HKDF `info` for a `prf` part, while keeping $I$ for the outer `combined` HKDF and AES-GCM AAD.

5. **High — §5.2, §6.2: `genesis` cannot compute slot info `I` without a circular dependency on `libraryID`**
   - **Problem:**
     - By §6.1, `libraryID` is the first 32 hex characters of SHA-256 of the exact `genesis` body.
     - By §6.2, the `genesis` body contains `keyring`, which in turn contains `slots` (§4.2).
     - By §5.2, every slot (`sealed`, `prf`, `combined`) encrypts the vault seed using `I = "colophon/vault-slot/4\n" ‖ libraryID ‖ "\n" ‖ vaultID ‖ "\n" ‖ kind ‖ "\n" ‖ join(controllers, ",")` as HPKE `info`/AAD and HKDF `info`/AES-GCM AAD.
     - Because `sealed` uses randomized HPKE encapsulation (`enc` and `ciphertext`) and `prf`/`combined` use AES-256-GCM (`nonce ‖ ciphertext ‖ tag`) with AAD `I`, the slot ciphertexts inside `genesis.keyring.slots` depend on `I`, which depends on `libraryID`, which is the SHA-256 of the serialized `genesis` body containing `genesis.keyring.slots`!
   - **Failure scenario:** It is mathematically impossible to construct a valid `genesis` entry with any slot in `genesis.keyring.slots`, because computing the slot's ciphertext/tag requires knowing `libraryID` (the hash of the `genesis` body), which changes as soon as the slot's ciphertext/tag is placed into the `genesis` body. (And if `genesis` has `slots: []`, the host cannot persist the vault seed at genesis per §2.2: "The host persists it only inside a slot.")
   - **Proposed fix:** Either:
     1. Omit `libraryID` from `I` (binding to `vaultID` is already globally unique and library-specific if `vault` is freshly generated per library, and the slot itself is inside the signed authority chain which is bound to `libraryID`), OR
     2. Define `libraryID` from a pre-genesis seed / genesis controller / vault, or move initial `slots` (or `keyring` slots) out of the `libraryID` preimage. Replacing `libraryID` in `I` with `vaultID` alone (`I = "colophon/vault-slot/4\n" ‖ vaultID ‖ "\n" ‖ kind ‖ "\n" ‖ join(controllers, ",")`) is the simplest fix and matches the Swift implementation's ability to build slots before encoding the genesis body.

6. **High — §8, §2.2, §5.2: Two-phase host ceremony cannot create a `prf` or `combined` slot and sign `genesis` or `keyring` in "one prompt per action" on WebAuthn**
   - **Problem:** §8 states: "**One prompt per action:** the core returns every body that one action needs before asking for any signature, so the host can collect all of them in one ceremony per key." However, creating a `prf` slot (or a `combined` slot with a `prf` part) for the vault seed requires the 32-byte `prfOutput` from the WebAuthn authenticator (`evalByCredential` / PRF extension) **before** the `box` (`AES-256-GCM(key = HKDF(prfOutput, ...), plaintext = seed)`) can be computed. And `box` is a field inside `keyring.slots` inside the `genesis` or `keyring` authority entry `body`! Meanwhile, the WebAuthn signature on that `genesis` or `keyring` entry must sign `challenge = SHA-256(body)`.
   - **Failure scenario:** When creating a library (`genesis`) with a passkey PRF slot, or rotating the vault (`keyring`) with a passkey PRF slot, the core cannot return the `body` to be signed before the passkey evaluates the PRF extension on the new `salt`, because `body` contains `keyring.slots[i].box`, which encrypts the vault seed under the PRF output. Therefore, the passkey must be prompted *twice* (once to evaluate PRF on `salt` so the core can build `box` and produce `body`, and a second time to sign `SHA-256(body)`), violating §8's normative requirement ("the core returns every body that one action needs before asking for any signature, so the host can collect all of them in one ceremony per key").
   - **Proposed fix:** Update §8 to acknowledge the two-ceremony requirement when sealing a new PRF slot, or separate slot publication from authority signing: "When an action creates a new `prf` slot (or `prf` part) for a passkey that has not yet evaluated the slot's `salt`, the host MUST first evaluate PRF for `salt` to construct the slot's `box`, after which the core returns the complete authority body for signing."

7. **High — §8, §6.2: Vault rotation with a passkey controller cannot open historical epochs and sign the `keyring` entry in a single WebAuthn ceremony**
   - **Problem:** During controller removal (§6.4), the vault MUST rotate. Under §6.2, a vault-rotating `keyring` entry contains `shares` (every existing epoch re-sealed to the new vault) and `epochs` (fresh epochs for every namespace). If the vault is currently locked and the user is unlocking it via a passkey (`prf` slot) *and* signing the `keyring` entry with that passkey:
     - To construct the `keyring` entry `body`, the core must first decrypt all existing epochs (to re-seal them into `shares` inside `body`), which requires opening the *current* vault's `prf` slot first.
     - Only after the host runs a WebAuthn assertion to get the current vault's PRF output can the core decrypt existing epochs, seal `shares` to the new vault, and assemble the `keyring` entry `body` whose `SHA-256(body)` is the WebAuthn challenge for signing the `keyring` entry.
   - **Failure scenario:** An implementer following §8 ("the core returns every body that one action needs before asking for any signature, so the host can collect all of them in one ceremony per key") attempts to combine vault unlock and `keyring` signing into a single WebAuthn ceremony. Because the WebAuthn `challenge` must equal `SHA-256(body)` (§3.3 step 1), and `body` cannot be constructed until the old vault is unlocked and `shares` are encrypted, the single-ceremony model in §8 is unimplementable whenever the vault is not already unlocked in the session.
   - **Proposed fix:** Clarify in §8 that **Open the vault** is a prerequisite phase before **Prepare an authority change** whenever the authority change (`grant`, `revoke`, `rekey`, or vault-rotating `keyring`) requires reading or sealing namespace epochs and the vault seed is not yet in session memory.

8. **High — §3.3: WebAuthn origin matching is underspecified and vulnerable to label/URL injection compared to the Swift reference**
   - **Problem:** §3.3 step 1 states: "`origin` equal to `https://<rp>` or `https://<label>.<rp>`".
     - In the Swift reference (`Controller.swift` lines 83–95), `origin(_:matches:)` checks:
       1. `host` contains none of `/`, `:`, `?`, `#`, `@`, `\`.
       2. Allows multi-label subdomains (`https://<labels>.<rpID>`), not just a single `<label>`, provided `!labels.hasPrefix(".") && !labels.hasSuffix(".") && !labels.contains("..")`.
     - In 0.4 §3.3, "<label>" is undefined:
       1. If an implementer treats `<label>` as any non-empty string without checking for `@`, `/`, `?`, `#`, or `:`, an origin like `https://evil.com@id.luff.works` or `https://evil.com/.id.luff.works` matches `https://<label>.<rp>`!
       2. Conversely, if an implementer treats `<label>` as a single DNS label (no dots), then `https://a.b.id.luff.works` is rejected by 0.4 but accepted by the Swift reference (`KeyringTests.swift` / `Controller.swift`).
       3. Also, §2.1 does not forbid `rp` from being empty or containing `/`, `:`, `@`, uppercase letters, or leading/trailing dots (Swift `Controller.swift` line 64 & `Keyring.swift` line 86 at least check `!rpID.isEmpty`).
   - **Failure scenario:** A verifier implements `origin` matching as `origin == "https://\(rp)" || (origin.hasPrefix("https://") && origin.hasSuffix(".\(rp)"))`. An attacker on `https://attacker.example?.id.luff.works` or `https://attacker.example#@id.luff.works` (or via a crafted `clientData` with userinfo `https://user@id.luff.works`) passes the suffix check, or a multi-label subdomain `https://app.staging.id.luff.works` is accepted by Swift and rejected by Rust.
   - **Proposed fix:** Define both `rp` validation (§2.1) and `origin` matching (§3.3) explicitly:
     - In §2.1: "`rp` MUST be a non-empty valid domain name (lowercase ASCII letters, digits, `-`, and `.`, with no empty labels and no leading or trailing `.`)."
     - In §3.3 step 1: "After stripping the required prefix `"https://"`, the remainder `host` MUST be non-empty, MUST NOT contain `/`, `:`, `?`, `#`, `@`, or `\`, and MUST either equal `rp` or end with `.` ‖ `rp` where the prefix before `.` ‖ `rp` is non-empty, does not start or end with `.`, and does not contain `..`."

9. **High — §6.4, §6.2: "Removing a controller, or taking a role away from one, MUST rotate the vault" is not wired into §6.3 verification rules or error codes**
   - **Problem:** §6.3 says: "The verifier tries the control rule first. If that fails, it tries the recovery rule, and if both fail the entry is refused with `badSignature`." Where does the verifier check §6.4 ("Removing a controller, or taking a role away from one, MUST rotate the vault (§6.2). It's authorized only by the control rule. The removed controller's slots MUST be absent from the new keyring")?
     1. If a `keyring` entry is signed by the control threshold, removes a controller (or removes a role from a controller), and does *not* change `keyring.vault`, what error does the verifier return (`malformed`, `brokenAuthorityChain`, or `badSignature`), and is it checked during `replay`?
     2. What if a controller's `key` is kept (same controller ID), its `roles` are unchanged, its `label` is changed, or its `verification` is changed from `true` to `false` (or omitted)? Lowering `verification: true` to `false` weakens security on a controller without rotating the vault or being treated as taking a role away.
     3. What if a controller is *not* removed, its roles are unchanged, and its slot is removed, or what if a controller's `roles` are reduced (e.g. from `["control", "approve"]` to `["approve"]`): §6.4 says "The removed controller's slots MUST be absent from the new keyring." Does a *demoted* controller (one that had a role taken away, but is still in `controllers`) have to lose its slots, or only a removed controller?
   - **Failure scenario:** Implementer A requires a controller whose role was reduced from `["control", "approve"]` to `["approve"]` to have no slots in the new keyring; Implementer B allows the demoted controller to have a slot for the new vault because it is still an active controller in `keyring.controllers` (§4.2 "Every slot names existing controllers"). A library with a demoted controller is accepted by B and permanently rejected by A.
   - **Proposed fix:**
     - In §6.4, state explicitly: "If any controller present in the previous keyring is absent from the new keyring, or if any role present in its previous `roles` is absent from its new `roles`, `keyring.vault` MUST differ from the previous `vault` (rotating the vault per §6.2). A controller that remains in `controllers` with fewer roles MAY have slots for the new vault; a removed controller is no longer in `controllers` and therefore cannot be named by any slot (§4.2). Violation of this rule MUST be rejected as `malformed`."

10. **Medium — §7, 0.3 §7.2: `colophon.importBatch` is a "root-only engine operation" in 0.3, which is broken in 0.4 because `root` no longer exists and controllers cannot author operations**
    - **Problem:** §1 and §7 state that 0.3 §5–§8 are kept as they are. In 0.3 §7.2 (lines 487–499): "`Reducers receive kind, immutable grant and root role from verified authority... colophon.importBatch is a root-only engine operation... Only this authenticated root publication can confer imported-baseline semantics.`" Furthermore, in 0.3 (`authority.rs` lines 189–204), `root` was automatically inserted into `Authority.members` at genesis with `grant: None` (unrestricted write access to all namespaces), so `root` could author operations in `ops/<rootID>/...`.
      In 0.4:
      1. There is no `root` identity! There are only `controllers` (which can be WebAuthn passkeys without agreement keys and without `Member` entries or grants) and `vault` (whose private key is never held as a signing member identity).
      2. Are controllers automatically members who can write operations in `ops/`, or must every writer (including the owner's device) be admitted via a `grant` entry? §7 says "Requests, grants, member kinds, the pairing code, expiry and write budgets work as in 0.3 §4." In 0.3 §4, `root` was never granted via `grant`—it was implicitly a member from `genesis`!
    - **Failure scenario:**
      1. A newly created 0.4 library has `genesis` + `rekey`, and no `grant` entries yet. The owner tries to write a note or save a link on their device, or run `colophon.importBatch`. If controllers are not implicitly members, no key can author any operation until the owner creates a separate member identity, creates a `request`, and signs a `grant` to themselves! And even after a `grant`, no member has the `root` role required by 0.3 §7.2 for `colophon.importBatch`, so `colophon.importBatch` is permanently unusable in 0.4.
      2. Conversely, if an implementer assumes `control` controllers *are* implicit members, a `webauthn` controller cannot sign operations unless operations support WebAuthn assertions, and §4.1 forbids a controller key from being an `agent`/`server` member (implying a controller key *could* be granted as a `device`/`app` member, which conflicts with 0.3 `grant` rules if it's already in `members`).
    - **Proposed fix:** Explicitly specify in §7:
      1. Controllers and the vault are **not** members and cannot author operations directly; every operation author (including the owner's device and the §9 copy tool's copying member) MUST be admitted as a member through a `grant` entry.
      2. Define how 0.3 §7.2 `colophon.importBatch` authorization works in 0.4 (or state whether `colophon.importBatch` is authorized by any non-caveated `device`/`app` member, or removed in favor of §9's `imported` field).

11. **Medium — §9 vs 0.3 §5 / §7.2: Clean copy references `imported: {"library": <old ID>, "signedBodyDigest": <exact old body digest>}` and `imports.rs`, which is undefined in 0.4 and 0.3**
    - **Problem:** §1 states that 0.4 "leaves operations, modules and HTTP exchange (§5–§8) as they are." Yet §9 Step 3 states: "Imports operations through the existing import contract (`imports.rs`). Each copied operation is re-signed by the copying member and carries `imported: {"library": <old ID>, "signedBodyDigest": <exact old body digest>}`."
      In 0.3 §5 (lines 178–198), neither the operation plaintext nor the signed operation header defines an `imported` field, and 0.3 §5 states: "The first nine metadata fields, excluding `nonce` and `ciphertext`, are canonicalized as AES-256-GCM associated data." If `imported` is on the signed header, is it included in the AES-256-GCM associated data? If `imported` is inside the operation plaintext, is it included in the `colophon/operation-id/3` preimage (`operation` with `id: ""`)? What validation rules apply to `imported.library` (32 lowercase hex?) and `imported.signedBodyDigest` (64 lowercase hex?)?
    - **Failure scenario:** Two implementations of 0.4 implement §9 clean copy: one places `imported` in the signed operation header (or includes it in AAD), and the other places `imported` in the encrypted operation plaintext. Copied libraries fail AEAD decryption or `operation-id` verification across implementations.
    - **Proposed fix:** In §9 (or §5), specify the exact JSON location, field types, AAD inclusion, and `colophon/operation-id/3` inclusion of `imported: {"library": "<32 hex>", "signedBodyDigest": "<64 hex>"}`.

12. **Medium — §6.1, §6.2, 0.3 §4: `revoke` and `rekey` epoch requirements when a library has no epochs yet, or when a revoked member had no readable namespaces**
    - **Problem:**
      1. In §6.2, `genesis` says: "Creates the library and its first keyring. The initial epochs follow in a `rekey`." What if an authority log has a `grant`, `keyring`, or `layout` at `seq: 2` *before* the initial `rekey`? In 0.3 (`authority.rs` line 519), `rekey` only checks that epochs in `rekey.epochs` are consecutive starting at 1, and doesn't require `seq: 2` to be `rekey` or to cover all declared `namespaces`!
      2. In §6.2, when a `keyring` entry rotates the vault: "`shares` MUST seal every existing epoch to the new vault, and `epochs` MUST start a new epoch in every namespace sealed per §5.1." What if vault rotation happens at `seq: 2` before the initial `rekey` (when no epochs exist yet)? Then `shares` is `[]` and `epochs` creates epoch 1 for every namespace. Is `epochs` in `rekey` or `keyring` required to be non-empty?
      3. In 0.3 §4 (`authority.rs` lines 366–388), `revoke` requires rotating every readable namespace in the member's grant. Since 0.3 §4 states "Namespace and access arrays MUST be nonempty; write implies read", every granted member has `read` on at least one namespace. However, if a `grant` happens before the initial `rekey` (or if a member's grant has already expired at `revoke.issued`), must `revoke` still rotate all namespaces in the member's grant?
    - **Failure scenario:** A `keyring` entry rotating the vault or a `grant` entry is placed at `seq: 2` before `rekey` has initialized epoch 1 for all declared namespaces. In `grant`, `add_shares` expects shares for existing epochs (0 epochs), so the member receives no keys at `seq: 2`, and if `rekey` at `seq: 3` fails to include the member or if operations cite `seq: 2`, epoch lookup fails.
    - **Proposed fix:** In §6.2, specify: "Sequence 2 (`seq: 2`) MUST be a `rekey` (or `genesis` MUST be immediately followed by a `rekey` before any `grant`, `revoke`, or vault-rotating `keyring`) that introduces epoch 1 for every declared namespace in `genesis.namespaces`." Also require `rekey.epochs` to be non-empty.

13. **Medium — §4.2, §6.2: Canonical representation of `recoverThreshold`, `verification`, `shares`, and `epochs` (omitted vs explicit default/empty)**
    - **Problem:** Colophon 0.3 §2 (kept by 0.4) requires canonical JSON encoding and states that `previous` is `null` at genesis, while optional fields on other structs are omitted when absent. In 0.4:
      1. In §4.2, the example shows `"recoverThreshold": 1`, and says "`recoverThreshold` is between 1 and the number of `recover` controllers, or 0 when there are none." Yet in the Swift reference (`Keyring.swift` line 9 & `KeyringHolder.swift` line 267), `recoverThreshold` is **omitted** (`nil`) when 1, and `KeyringRules.thresholdFault` (line 132) explicitly rejects an explicit `recoverThreshold: 1` as non-canonical (`if let recoverThreshold, recoverThreshold <= 1 ... return .recover`)!
      2. In §4.1, `verification` is "Optional, `webauthn` only. Require UV on every signature by this controller." Is `"verification": false` allowed on a `webauthn` controller, or must it be omitted when false? Must `verification` be absent (not `false`) on a `raw` controller?
      3. In §6.2, `keyring` has "`keyring`, and also `shares` and `epochs` when the vault changes". When the vault does *not* change, must `shares` and `epochs` be omitted from the JSON object, or can they be `[]` / `null`?
      4. In §3.1, when there are no cosignatures, "`cosignatures` are present only when used" — so `cosignatures: []` MUST be rejected as malformed.
    - **Failure scenario:** The Swift reference rejects any `keyring` with explicit `"recoverThreshold": 1` and cannot represent `"recoverThreshold": 0` (line 266: `guard proposal.recoverThreshold >= 1`), whereas a Rust implementer following §4.2 literally always serializes `"recoverThreshold": 1` or `"recoverThreshold": 0`. Every conformance vector and authority record fails cross-implementation validation.
    - **Proposed fix:** State explicitly in §4.1, §4.2, §3.1, and §6.2:
      - In §4.2: "`recoverThreshold` is always a required integer field in 0.4 (`0` when there are no `recover` controllers, or `1..=count(recover)` when at least one `recover` controller exists)." (Note in §10 that this intentionally differs from Swift's 0.1 omission of `1`.)
      - In §4.1: "On `raw` controllers, `verification`, `rp`, and `credential` MUST be absent. On `webauthn` controllers, `agreement` MUST be absent, and `verification` is either `true` or absent (`false` is allowed or forbidden—specify one)."
      - In §3.1: "An empty `cosignatures: []` array MUST be rejected with `malformed`."
      - In §6.2: "When `keyring.vault` is unchanged, `shares` and `epochs` MUST be absent."

14. **Medium — §2.3, §3.3: COSE_Key CBOR parsing and DER ECDSA verification rules have edge-case divergences from the Swift reference**
    - **Problem:**
      1. **COSE_Key CBOR (§2.3):** §2.3 says "A WebAuthn registration's COSE_Key MUST be a definite-length CBOR map with: `kty` (1) = 2 (EC2); `alg` (3) = -7 (ES256); `crv` (-1) = 1 (P-256); `x` (-2) and `y` (-3) as 32-byte strings. The key is `0x04 || x || y`. Any other shape, or an invalid point, MUST be rejected with `malformed`."
         - Does "Any other shape" mean extra map keys (such as `key_ops` (4) or `kid` (2), which some authenticators include in `credentialPublicKey`) are rejected, or ignored? Swift (`CBOR.swift` line 24: `guard fields.count == 5`) rejects any map with more than 5 entries, rejects non-canonical CBOR integer encodings, and rejects trailing bytes (`guard reader.finished`).
         - Does CBOR map key ordering matter, or is any definite-length 5-entry map without duplicate keys accepted?
      2. **ASN.1 DER ECDSA (§3.3 step 5):** §3.3 says "A verifier MUST accept only DER that is minimally encoded, with r and s in [1, n-1]."
         - In the Swift reference (`Controller.swift` line 76), verification uses Apple CryptoKit's `P256.Signing.ECDSASignature(derRepresentation: signature)` and `key.isValidSignature(parsed, for: message)`. On Apple platforms (CoreCrypto / BoringSSL), `derRepresentation` parsing and `isValidSignature` have specific behavior, whereas in Rust `p256::ecdsa::der::Signature::from_der` and `VerifyingKey::verify` by default **reject high-S signatures** (`s > n/2`) in `ecdsa::hazmat::verify_primitive` unless `Signature::normalize_s()` is called before verification!
    - **Failure scenario:** A Rust implementer uses `p256::ecdsa::VerifyingKey::verify` on a `p256::ecdsa::der::Signature` (or converts DER to `p256::ecdsa::Signature` and calls `.verify()`). Because the RustCrypto `p256` crate enforces low-S inside `verify()`, real WebAuthn assertions from authenticators (which produce high-S ~50% of the time) fail verification in Rust even though DER parsing succeeded!
    - **Proposed fix:**
      - In §2.3: Specify that the CBOR byte slice MUST contain no trailing bytes, no duplicate keys, and exact 5 entries `{1, 3, -1, -2, -3}` with minimal CBOR integer/length headers.
      - In §3.3 step 5: Explicitly note for implementers: "If the underlying ECDSA library enforces low-S during verification (such as Rust `p256`), the verifier MUST normalize `s` to `min(s, n - s)` after validating minimal DER encoding and `r, s in [1, n - 1]`."

15. **Medium — §6.3, §4.2: Unauthenticated DoS and error precedence between `newerFormat`, `malformed`, and `badSignature`**
    - **Problem:**
      - §6.3 states: "The verifier tries the control rule first. If that fails, it tries the recovery rule, and if both fail the entry is refused with `badSignature`. An unknown kind or field MUST stop replay with `newerFormat`, before any content is read."
      - Compare with 0.3 §4 (lines 134–138 and `authority.rs` lines 227–240, 593–603): In 0.3, a reader MUST reject only an **authenticated** unsupported layout or unknown authority kind with `updateRequired` (`newerFormat`). Unauthenticated garbage or an unknown `kind` without a valid signature from current authority is rejected as a signature/malformed error, so an unauthenticated attacker (or corrupt file) cannot force a client into the sticky `updateRequired` / `newerFormat` state (which in 0.3 §4 tells the user to update the app and refuses to open the library).
      - In 0.4, §2.1, §4.1, §6.3, and §10 say unknown `form`, `role`, `slot kind`, or `authority kind/field` MUST fail with `newerFormat`. If a verifier checks unknown `form`/`role`/`slot kind`/`kind` *before* verifying the entry's signatures against the *current* keyring (for `seq > 1`), an unauthenticated attacker can inject a single unsigned record with an unknown `kind` or `role` and trigger `newerFormat` (`updateRequired`). Conversely, for `genesis` (`seq == 1`), the signers are inside `genesis.keyring.controllers`—if a `control` controller in `genesis` has `"form": "quantum"`, you *cannot* verify its signature first!
    - **Failure scenario:** An implementer checks signatures before checking unknown fields on `seq > 1` (following 0.3 `authority.rs`), while the §10 conformance test provides an unsigned or dummy-signed record with an unknown `role` and expects `newerFormat`. Or conversely, an implementer checks `newerFormat` before signature verification on `seq > 1`, allowing an unauthenticated relay or peer to brick a client into the `updateRequired` state by serving a forged authority entry with `"kind": "future"`.
    - **Proposed fix:** In §6.3, specify the exact verification order:
      - For `seq == 1` (`genesis`), check unknown `kind`, `form`, `role`, or `slot.kind` before signature verification and return `newerFormat`.
      - For `seq > 1`, verify the entry's signatures against the **current** keyring (prior to `seq`) *before* reporting `newerFormat` for an unknown `kind`, `form`, `role`, or `slot.kind` in the new entry. An entry at `seq > 1` whose signatures do not satisfy the current keyring's control or recovery rule MUST fail with `badSignature`, never `newerFormat`.

16. **Low — §4.2, §5.2: Slot validation rules and duplicate/ordering constraints on `slots` and `controllers`**
    - **Problem:**
      - §4.2 says "`controllers` is sorted by ID, with no duplicate IDs." It does not state whether `roles` inside a `Controller` must be sorted or free of duplicates (e.g., `["control", "control"]`), nor whether `slots` has any ordering requirement or may be empty (`slots: []`).
      - §5.2 says "Every slot has `kind`, `controllers` (the IDs whose keys open it, in order), and `label`."
        1. For `sealed`, the table says: "The single controller's `raw` key with `agreement` opens it." It does not explicitly state that `slot.controllers` MUST have length 1 (`controllers.len() == 1`), that the named controller MUST have `form == "raw"` and `agreement` present, and that `sealed` (`enc` and `ciphertext`) must be structurally valid (65-byte valid SEC1 point `enc` and 48-byte `ciphertext` for a 32-byte seed + 16-byte tag, as in `authority.rs` `validate_seals`).
        2. For `prf`, the table says: "The single controller is `webauthn`." It does not explicitly state that `slot.controllers` MUST have length 1, that the named controller MUST have `form == "webauthn"`, and that `box` MUST be 60 bytes (`12-byte nonce || 32-byte ciphertext || 16-byte tag`).
        3. For `combined`, `box` must also be 60 bytes, each `sealed` part must name a `raw` controller with `agreement` and have a 65-byte `enc` and 48-byte `ciphertext`, and each `prf` part must name a `webauthn` controller and have a 32-byte `salt`.
    - **Failure scenario:** A malformed slot (e.g. a `prf` slot naming two controllers in `slot.controllers`, or naming a `raw` controller, or with a 10-byte `box`) is accepted during `Authority::replay` because §4.2 only checks "Every slot names existing controllers", and later crashes or fails with `malformed` instead of `vaultLocked` only when a device tries to open it.
    - **Proposed fix:** Add explicit structural validation rules in §4.1 and §5.2:
      - In §4.1: "`roles` MUST contain no duplicates (and SHOULD/MUST be sorted lexicographically)."
      - In §5.2:
        - For `sealed`: `controllers` has length 1, naming a `raw` controller with `agreement`; `sealed.enc` is a valid 65-byte uncompressed P-256 point and `sealed.ciphertext` is 48 bytes.
        - For `prf`: `controllers` has length 1, naming a `webauthn` controller; `salt` is 32 bytes and `box` is 60 bytes.
        - For `combined`: `controllers` has length $\ge 2$ with no duplicates, `parts` has the same length as `controllers`, `box` is 60 bytes, and each `parts[i]` matches the `form` (`raw` with `agreement` for `sealed`, `webauthn` for `prf`) of `controllers[i]`.

17. **Low — §6.3: Ambiguity when `by` is not among the signers or when extra invalid/unauthorized cosignatures are attached**
    - **Problem:**
      - §3.1 states: "The primary signer is the body's `by`. Every cosignature signs the **same body bytes**. A primary signer and its cosigners MUST be distinct key IDs, and each MUST be a controller in the keyring that authorizes the entry (§6.3)."
      - §6.3 states:
        - For `rekey`, `grant`, `revoke`: "One controller with `approve`. A controller with `control` but not `approve` may sign `rekey`."
        - For `layout`: "One controller with `control`".
        - For `keyring`, by control: "Distinct current `control` controllers, at least the current `threshold`. UV is required."
      - Two ambiguities arise:
        1. On a single-signer action (`rekey`, `grant`, `revoke`, `layout`), are `cosignatures` forbidden (`MUST be absent`), or allowed if valid?
        2. On a `genesis` or `keyring` entry, must **every** signer (the primary signer `by` and every cosigner in `cosignatures`) hold the required role (`control` for the control rule, or `recover` for the recovery rule) and have a valid signature with UV? Or (as in Swift `AuthorityState.swift` line 91) does the verifier just count the subset of signers that verified and had the role? If a controller has both `control` and `recover` roles, and signs a `keyring` entry alongside a `recover`-only controller, the control rule fails (because the second signer lacks `control`) and the recovery rule succeeds (because both have `recover`).
    - **Failure scenario:** Implementer A rejects a `keyring` entry if any cosignature fails verification or lacks the `control` role before falling back to the recovery rule; Implementer B filters for valid signatures with `control`, then falls back to filtering for valid signatures with `recover`.
    - **Proposed fix:** In §3.1 and §6.3, state:
      - "Every signature on an envelope (the primary signature for `by` and every entry in `cosignatures`) MUST cryptographically verify against that controller's key in the authorizing keyring; any invalid signature or unknown signer ID immediately fails with `badSignature`."
      - "For `rekey`, `grant`, `revoke`, and `layout`, `cosignatures` MUST be absent."
      - "For `genesis` and `keyring`, the control rule succeeds iff `by` and every cosigner in `cosignatures` has the `control` role, has UV on WebAuthn assertions, and total signers $\ge \text{threshold}$. The recovery rule succeeds iff `by` and every cosigner in `cosignatures` has the `recover` role, has UV on WebAuthn assertions, `recoverThreshold > 0`, total signers $\ge \text{recoverThreshold}$, and the keyring diff satisfies the recovery add-only conditions."

### Answers to §11 Open Questions

1. **Should `custody` and `presence` be signed controller fields, or kept host-side display only?**
   Keep them **out** of the signed controller descriptor (or display-only). The core verifier cannot verify hardware attestation or physical custody at runtime, and changes to how a passkey is synced or stored by the OS would otherwise require a `keyring` authority transaction.

2. **Should `layout` require the control threshold rather than one signature?**
   **Yes, `layout` MUST require the control threshold (with UV on WebAuthn).** Raising `layout` is an irreversible, library-wide breaking change ("Never lowers the layout", and 0.3 §4 requires older clients to stop and enter `updateRequired` before reading or writing any content). In a `threshold: 2` library, a single compromised `control` key should not be able to unilaterally brick the library for all existing clients by raising `layout`.

3. **Should a keyring with only one `recover`-or-`control` key be refused, rather than warned about?**
   **No, keep it valid at the protocol level and warn in the host.** Automated tests, CLI tools, ephemeral/single-device libraries, and the initial step of progressive onboarding legitimately start with a single controller (`Genesis with one raw controller` in §10); enforcing a multi-key minimum in consensus would force hosts to invent throwaway dummy keys just to satisfy the verifier.

4. **Is high-S tolerance for WebAuthn DER acceptable? (Some verifiers require low-S.)**
   **Yes, high-S tolerance is required for WebAuthn.** FIDO2/WebAuthn authenticators (including platform passkeys and hardware security keys) do not normalize ECDSA signatures to low-S, and because the host cannot alter the `signature` bytes without access to the private key (or unless the host normalizes `s` to `n - s` before building the record), the verifier must either accept high-S DER (normalizing `s` in memory before calling low-S-only crypto libraries like Rust's `p256`) or require the host to normalize DER `s` before submission. Accepting high-S in the verifier is safer and simpler, because authority entries are hash-chained by `body` (not `signature`) so signature malleability does not affect `previous` digests or `libraryID`.

5. **Should the copy tool keep the old library ID as `importedFrom` on the genesis, for display only?**
   **Yes, as an optional display-only field (`importedFrom`: 32 lowercase hex characters) on `genesis`.** Because §9 already stamps every copied operation with `imported: {"library": <old ID>, ...}`, the old library ID is already present in the library; recording `importedFrom` once on `genesis` gives the ledger and UI a clean provenance record at sequence 1 without scanning operations, provided the spec explicitly states it carries no authority and does not alter `libraryID` derivation.
